SELF-PLAY WORKER LAUNCHER

Main class: _app.SelfPlayWorkerApp
Program arguments: one UTF-8 .properties configuration file
Working directory: project root is convenient but not required.
All relative paths INSIDE the file resolve against that file's directory.
Use forward slashes in Windows property paths; backslashes are escape characters.
Do not quote property values containing spaces.

Use a separate project copy. Do not rebuild the running collection's project.
After building the copy, run this main class with no arguments:

  _app.SelfPlayWorkerAppSelfCheck

It checks the launcher with synthetic workers and a real JVM shutdown fixture.
It does not play a game or require model binaries. Existing checks remain:

  testing.selfcheck.WorkforceSelfCheck
  jobs.SelfPlayWorkerSelfCheck

The launcher runs exactly one SelfPlayWorker through LocalWorkforce(1, 1).
It displays the job ID, output/log locations, changing progress messages,
dataset fingerprint and final manifest hashes. Failure exits nonzero with
the original cause; partial files and the process log remain for diagnosis.

Graceful JVM shutdown, including a normal terminal Ctrl+C, cancels the active
job and waits for its child-process cleanup. Interrupting the launcher thread
also cancels, waits, and restores interruption. Force-killing the JVM, some
IDE stop actions, power loss or OS termination may bypass shutdown hooks.
Do not assume a missing parent means its child has stopped.

Runtime setup
-------------
First package a frozen application JAR using jobs/self-play-worker.txt.
Keep the expected hash recorded at packaging; do not recompute it on retry.
Include each required dependency JAR explicitly with its own pinned hash.
The child does not inherit IntelliJ's classpath. A JAR manifest Class-Path
cannot supply extra dependencies. The launcher itself uses the project's
normal classpath, which may differ from the pinned child runtime.

There are no implicit settings or hash defaults. Unknown or missing keys,
invalid hashes/budgets and existing output fail. Hash contents are checked by
the worker before launching. For baseline scoring use value.file=baseline
and OMIT value.sha256; the supervised example below retains the value model.

This example reserves seed 752 for a one-game, 1902-limited smoke only.
Keep it out of training and strength evaluation. Seeds 496-751 remain the
running production collection; do not repeat or interrupt them.
No real smoke game has been run merely by creating these files.

Successful output is under data/self-play-worker-smoke-v1, with:
  process.log
  process.pid
  worker-complete.properties
  batch/manifest.json
  batch/cache/manifest.json

The worker validates file receipts, not playing strength. A one-game batch
may lack VALIDATION data and still be a successful smoke. Do not change its
split seed or collect extra games just to make that warning disappear.

Keep request.properties and all completed/partial output. If something fails,
inspect the exception and process.log. Confirm any old child has stopped
before a deliberate retry with the same settings/seeds in a NEW directory.
Do not overwrite output or include both attempts in a later corpus.
