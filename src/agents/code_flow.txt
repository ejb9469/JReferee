AGENTS PACKAGE: CODE FLOW
=========================

Purpose
-------
Choose a complete set of orders for one nation in non-press Diplomacy.

Search considers possible orders for every living nation, tries joint
submissions, and returns probabilities for the requested nation's actions.

This file describes the current implementation, including adaptive search and
optional payoff caching, movement scoping, and adaptive temperature.
Planned improvements are listed separately at the end.
There is currently no trained policy or value model. [ @ 11-06-26 ]

An order is one instruction. An action is one nation's complete submission
for the phase. A joint action contains one action for every living nation.
A policy is a probability distribution over actions.

Main route
----------
Caller supplies a position, processor settings, evaluator, and search budgets.
    -> Create an isolated search Game.
    -> Generate legal order options for each living nation.
    -> Construct and validate a small pool of complete actions per nation.
    -> DiLPiKLSearch solves those fixed pools.
         -> Sample one action per nation.
         -> Evaluate the joint action and each nation's alternatives.
              -> JointActionEvaluator checks its optional cache.
              -> Simulator.peek() resolves one phase and restores the root.
              -> Evaluator scores the successor, possibly using rollouts.
         -> Update action values and selection probabilities.
    -> AdaptiveDiLPiKLSearch optionally discovers additional actions.
         -> ResponseSearch tests new proposals against frozen opponent policies.
         -> Append accepted actions and solve the expanded pools from fresh Q.
    -> Return the final policy and diagnostics.
    -> Caller samples one complete action and submits its orders for real play.

The generation, simulation, evaluation, and search packages have separate jobs.
Generation proposes orders. Simulation determines what happens. Evaluation
assigns scores. Search decides how likely each proposed action is to be chosen.

1. Prepare the position
-----------------------
GameState is the immutable position being considered. It includes the phase
and board, with phase-specific information for retreats and adjustments.
Game is the mutable object used to resolve orders.

The caller supplies an isolated Game at the desired root position. Search
requires it to have no saved checkpoint. The requested nation must be alive.
A nation can remain alive through owned centers, stationed units, or pending
dislodged units; having no movement orders does not necessarily eliminate it.

Configure movement, retreat, and adjustment processors when creating the Game.
GameState does not carry processor configuration. If RolloutEvaluator is used,
its game factory must reproduce the intended processor settings.

MovementProcessor defaults to SzykmanJustice. JUDGE is an explicit alternative
that uses plain Judge with canonical order sorting. It is cheaper on some
positions but is not guaranteed to agree with the reference adjudicator.

2. Generate legal order options
-------------------------------
LegalOrderGenerator.generate(state, power)
    -> LegalOrderCatalog

The catalog belongs to one exact position and nation. It contains per-unit
options, current unit locations, and any build options and adjustment quotas.
LegalOrderCatalog.optionsFor(unit) returns that unit's options.

Movement:
    Options include holds, moves, supports, and possible convoys.
    The broad catalog can include convoy-dependent moves without an available
    fleet route. Catalog membership does not establish tactical success.

Retreats:
    Options concern dislodged units and use the preceding movement result.
    Omitting a unit's retreat order destroys that unit.

Adjustments:
    Builds are listed separately because they create units.
    Disband options identify existing units. The balance determines how many
    builds are available or how many disbands are required.

These are individual order options. They are not yet coordinated actions.

Optional movement boundary:
    ProvinceScope stores a fixed set of canonical provinces.
    ProvinceScope.restrict(state, catalog) keeps every owned unit and its hold,
    but removes orders whose target or auxiliary target lies outside that set.
    Issuing units must already be inside it, using current board locations.
    Coast-specific orders retain their exact targets.

The full board, owned centers, movement rules, and scoring are preserved.
The scope does not follow the occupied provinces as units move. An outside
unit is an error. This is a tactical-fixture tool; Diplodocus uses full-board
input and does not prescribe geographic clipping of actions.

3. Construct complete action candidates
---------------------------------------
ActionGenerationRequest(state, power, candidateLimit, seed)
    + LegalOrderCatalog
    -> ActionGenerator.generate(request, catalog)
    -> List<ActionCandidate>

Each ActionCandidate contains:
    power       The nation issuing the orders.
    orders      Immutable submitted orders for the current phase.
    logPrior    Natural logarithm of the action's fixed anchor probability.
    source      A label describing how the candidate was constructed.

The limit is a maximum, not a promise to return that many distinct actions.
The source label does not affect adjudication or payoff.

PlausibleActionGenerator is the default movement generator for the convenience
constructors of Search, DiLPiKLSearch, and RolloutEvaluator. It combines
supported attacks and defenses, possible support cuts, vacancy chains,
rotations, self-bounces, and attacks in different areas. A bounded beam fills
in the remaining orders. Some places are reserved for randomized exploration.
All-hold is first; a movement limit of one therefore gives only all-hold.
Movement pools are capped at 256 candidates.

Its own support orders are coordinated with the proposed friendly orders.
Foreign support can still appear, and depends on what that foreign nation
actually submits. Construction uses board geometry and ownership, not the
opponents' current search probabilities.

UniformActionGenerator is the simpler baseline. Its default movement
proposals exclude convoys. PlausibleActionGenerator also excludes convoys
and delegates retreats and adjustments to the uniform generator.

FriendlyConvoyUniformActionGenerator is an optional alternative. It requires
matching friendly convoy orders and a connected route of friendly sea fleets.
The route can still be disrupted during adjudication. Convoy-enabled adaptive
search also needs a compatible anchor; ActionPrior.convoyFreeUniform cannot
score those convoy actions.

ScopedActionGenerator wraps a generator for a movement experiment:
    Filter the catalog before constructing actions.
    Validate the returned actions against that filtered catalog.
    Restore each action's logPrior from an anchor bound to the full state.

Its default anchor is ActionPrior.convoyFreeUniform. A constructor accepts
a different state-to-anchor factory. The factory is called for the actual
movement state, so rollout anchors are not bound to an earlier root.
Use the same scope for initial, response, and continuation movement generation.
Retreat and adjustment generation passes through unchanged. A retreat or build
outside the scope will cause an error if later scoped movement reaches it.

4. Validate actions and retain their anchor probabilities
---------------------------------------------------------
CatalogActionValidator.validate(state, candidate, catalog)
    -> List<ActionValidationError>

Movement requires one order for every owned unit. Retreat orders may be
omitted. Builds may be left unused or waived, but every required disband must
be named. The validator checks phase, catalog membership, duplicate orders
for a unit, duplicate build sites, and adjustment quotas.

Validation does not guarantee matching foreign support, a surviving convoy,
or a successful attack. The generator handles its coordination rules;
adjudication determines the outcome.

SearchSupport prepares and checks pools for exactly the living nations.
Each pool must be nonempty and contain distinct valid actions. An empty
submission is still an ActionCandidate when the nation has nothing to order.
Action equality for pool/cache keys ignores order-list order and source
metadata, but preserves repeated-order counts, including repeated waives.

The anchor is a fixed reference policy for the position. It is separate from
both the generator's construction ranking and the search's final policy.
The current plausible movement generator uses a factorized uniform anchor.
Its tactical ranking changes which actions are offered, not their logPrior.

ActionPrior.logProbability(power, orders) supplies the fixed anchor value
when adaptive search examines new actions. Existing actions keep their
logPrior as the pools expand. The supplied initial priors must match it.
Negative infinity means zero anchor probability.

ActionDistribution.fromPriors(candidates) conditions anchor probabilities
on the retained pool. This normalization does not rewrite candidate priors.
DiL-piKL assigns zero mass to zero-prior actions and requires positive support
somewhere in every pool.

Caller-supplied movement pools and diagnostic probes bypass generation.
Check them with ProvinceScope.requireWithin(state, candidate) before solving
or evaluating a geographically restricted fixture. This also checks complete
orders against the scoped catalog. General solve() calls remain unrestricted.

5. Solve the fixed pools
------------------------
DiLPiKLSearch.search(game, power)
    -> Generate pools and return one SearchResult.

DiLPiKLSearch.solve(game, pools)
    -> Solve supplied pools and return one JointSearchResult.

Overloads accept a shared JointActionEvaluator. Without it, these entry
points create an uncached helper.

Q stores each action's running mean raw payoff. It starts at zero.
Lambda controls how strongly the policy follows its anchor:

    probability(action) is proportional to
        exp((Q(action) + lambda * logPrior(action)) / (kappa + lambda))

Both Q and logPrior are divided by the full denominator. Equivalently:
    logit = Q / (kappa + lambda) + lambda / (kappa + lambda) * logPrior

Larger lambda gives the anchor more influence. LambdaDistribution supplies
the population's positive lambda values and their probabilities. agentLambda
controls the policy returned for play. Both must suit the evaluator's scale.

Each iteration:
    a. Form the type policies from the previous completed Q and temperature.
       Independently sample a population lambda and action for every nation.
    b. Freeze the resulting joint submission before updating any Q values.
    c. Evaluate that joint submission.
    d. For each nation, replace only its action with each other candidate.
       Keep the sampled opponents unchanged and evaluate the replacement.
    e. Update the running mean for every candidate.
    f. For each lambda type, observe the dot product of its frozen policy
       with this iteration's counterfactual payoff vector. Update its utility
       moments for the next iteration. All types share Q but keep separate
       moments. An output-only agentLambda is tracked without affecting play.

The played joint payoff is reused for each nation's sampled action.
For pool sizes K_i, an iteration requests 1 + sum_i(K_i - 1) joint evaluations.
A deterministic cache can reduce the actual simulations.
Cache hits still contribute Q updates and utility observations.

Pools and priors remain fixed during this solve. Iterations improve estimates
at the same root; they do not increase rollout depth or add missing actions.
Q describes sampled opponent history, not fresh values against the final
opponent policy. The returned policies use final Q, not a time average.

Constructors without a temperature argument preserve TemperatureSchedule.ZERO.
Explicit TemperatureSchedule.ADAPTIVE enables the Section 2.2 schedule:

    kappa_t = 3 S_t / (10 sqrt(t))
    S_t = population standard deviation of t policy-averaged raw utilities

Each completed search iteration contributes one equally weighted observation.
At t=0 the adaptive policy is uniform over positive-prior actions, represented
by the infinite-temperature limit. One observation has zero variance.
Final agent policies and population mixtures use completed Q and completed
type temperatures. Negative-infinity priors always retain zero probability.

The paper gives the formula but leaves the variance estimator and startup
details unspecified. Per-type policy-averaged observations and uniform startup
follow the public implementation in fairdiplomacy/agents/bqre1p_agent.py and
dipcc/dipcc/cc/cfrstats.cc, inspected at revision
e85afeddb34f5b7c1ea0827203b425a0f7e68ead of facebookresearch/diplomacy_cicero.
The release also uses linear weighting and numerical floors. Here Q retains
Algorithm 1's equal-weight update; utility observations use the same weighting.
No variance floor or prior smoothing is added. Returned policies remain
final-iterate policies.
This implements the full formula; it is not a bit-for-bit port of the release.

6. Resolve and score a joint action
-----------------------------------
JointActionEvaluator.evaluate(Map<Nation, ActionCandidate>)
    -> Map<Nation, Double>

The helper is bound to one Game, root position, and Evaluator instance.
It requires exactly one action for every living nation.

On an uncached evaluation:
    a. Simulator.peek(game, actions) validates the joint submission.
    b. It takes a checkpoint and resolves the current phase through Game.
       Game dispatches movement, retreat, or adjustment processing.
    c. It captures the successor GameState and restores the root in finally.
    d. The helper calls evaluator.evaluate(successor).
    e. It checks that every nation has a finite score.

The root is already restored before successor evaluation starts.
Candidate priors and source labels do not influence resolution.
Generation, validation, simulation, and evaluation failures are reported.

JointActionEvaluator.deterministic(...) enables a bounded least-recently-used
payoff cache. A hit returns the stored scores without simulation or evaluation.
Only successful, complete, finite results are cached.

Caching requires the same joint submission to produce the same scores every
time. It is an explicit caller promise, not something inferred from a seed.
Changing or freshly randomized evaluations must use uncached(...).
Create a new helper when the root or evaluation configuration changes.

7. Evaluate the successor
-------------------------
Evaluator.evaluate(state) returns scores for all seven nations, including
eliminated nations. Higher scores represent better outcomes for that nation.

SCEvaluator:
    Returns raw counts of owned supply centers.

ScoringEvaluator:
    Applies the selected ScoringSystem to recorded center ownership.
    It evaluates the position as if play stopped there; it does not declare
    a solo, a draw, or the end of the game.

RolloutEvaluator:
    Continues a successor through the rest of its year, then calls a leaf
    evaluator such as ScoringEvaluator. Multiple trajectories are averaged.

For each rollout evaluation:
    a. A winter input is scored immediately.
    b. Otherwise, the configured factory creates a separate continuation Game.
    c. Each trajectory takes one checkpoint.
    d. Generate fresh pools for each living nation at each subsequent phase.
    e. Sample complete actions using ActionDistribution.fromPriors(...).
    f. Use Simulator.advance() to keep advancing this continuation Game.
    g. Stop at the first winter adjustment position, before winter orders.
    h. Score the leaf and restore the trajectory checkpoint in finally.

Fall ownership is updated after completed Fall retreats. This boundary lets
movement choices affect center-based scores before the leaf is evaluated.
Rollouts use their own generator and anchor-weighted sampling; they do not
reuse root policies or run a new DiL-piKL solve at every future phase.

Simulator.advance() owns no checkpoint. Its caller handles recovery.
Game has one saved checkpoint, not a stack. Root peeks and rollout trajectories
therefore use separate games. Custom processor state and external records are
outside rollback; concurrent work also requires independent mutable games.

8. Discover missing responses and solve again
--------------------------------------------
AdaptiveDiLPiKLSearch wraps DiLPiKLSearch and ResponseSearch.
Its convenience entry point generates plausible initial pools. The explicit
entry point accepts initial pools, an ActionPrior, and optionally a shared
JointActionEvaluator.

After the initial fixed-pool solve:
    a. Freeze all nations' final population policies.
    b. ResponseSearch generates fresh complete proposals.
    c. Apply the fixed anchor; reject duplicates and zero-prior actions.
    d. Sample opponent actions from those frozen policies.
    e. Re-evaluate incumbents and proposals on the same opponent samples.
    f. Select proposals exceeding the best incumbent's mean raw payoff by
       more than minimumGain, subject to additionsPerNation.
    g. Apply pool limits and append accepted actions for all nations together.
    h. Solve the expanded pools from zero Q and fresh utility moments before
       returning any new policy.

Current proposal construction does not inspect the frozen opponent policies.
Only proposal evaluation uses them. ResponseSearch is a bounded heuristic,
not an exhaustive best-response calculation or a regularized optimality test.

Expansion currently applies to movement. Other phases receive one fixed-pool
solve. Stop reasons are ROUND_LIMIT, POOL_LIMIT, NO_RESPONSE_FOUND, and
NON_MOVEMENT. None proves equilibrium or adequate proposal coverage.

ResponseSearch.Report records duplicate, zero-prior, below-gain, addition-limit,
and selected decisions. AdaptiveDiLPiKLSearch.Result retains completed solves,
discovery reports, and additions blocked by pool limits.

9. Return a policy and play
---------------------------
SearchResult contains an ActionDistribution, aligned meanValues, and
samplesPerCandidate. In DiL-piKL the sample count is the iteration count;
it is not the number of cache misses or rollout trajectories.

JointSearchResult contains agent-lambda results for every living nation and
populationPolicies mixing their final-Q lambda-type policies.
Its temperatures map records final kappa by nation and lambda, including an
output-only agentLambda. temperature(nation, lambda) returns a recorded value;
it reports an error for an untracked type. The older two-argument result
constructor remains available but supplies no temperature diagnostics.
AdaptiveDiLPiKLSearch.Result.result() returns the requested nation's result
from the last completed solve.

The caller can choose an action with:

    ActionCandidate chosen = result.distribution().sample(random);

Submit chosen.orders() to the real game or server. Sampling preserves the
returned mixed strategy; always choosing the most probable action changes it.
Simulated opponent orders are predictions, not orders to submit for opponents.

A local match runner must gather independently selected submissions for all
nations, resolve the real phase, and repeat from the new position. Search
does not run that match loop or decide game termination and draw agreements.
Those are caller responsibilities.

Alternative baseline: Search
----------------------------
Search uses the same generation, simulation, and evaluation components.
It samples opponents from fixed anchor-conditioned pools, measures every
requested-nation candidate on those samples, and splits probability evenly
among exact best-value ties. It does not update opponent policies or perform
DiL-piKL regularization. It is a useful comparison baseline.

Diagnostics
-----------
CounterSearchApp and CounterSearchConsoleApp exercise a small two-player
position. They compare controlled and plausible pools and plain/reference
adjudication. Their settings are demo choices, not global package defaults.
The movement boundary is {Pic, Bur, Tyr, Bel, Ruh, Mun}; root, response, and
continuation generation share it. The fixture validates explicit probes and
initial plans against that scope. France still owns Paris, Marseilles, and
Brest; Germany retains Berlin and Kiel. Unoccupied outside centers remain on
the board, but scoped actions cannot move to them.

Options.standard() selects ADAPTIVE temperature. The existing four-argument
Options constructor retains ZERO; the five-argument constructor chooses
explicitly. The browser has a temperature selector. Console diagnostics v3
compare both schedules over complete two-action pools, then use ADAPTIVE for
response expansion. Output includes final kappa per nation at the demo lambda.

Fresh values are recomputed against the final opposing policy.
Within-pool gap compares the current policy's raw payoff with its best
retained action. Missing-probe gap compares named probes with that best
retained action. Neither measures all omitted legal actions.

Response residual compares the returned policy with a regularized response
formed from fresh values with kappa=0, using the three-argument policy helper.
The equilibrium-response definition is unchanged; a finite search temperature
can contribute to its residual. The demo uses a single lambda. Multiple lambda
types need type-aware checks. Raw gaps can remain positive under intended
regularization; NO_RESPONSE_FOUND does not measure policy convergence.

JointActionEvaluator and MovementProcessor expose work counters.
PerformanceStats records timings, with overlapping nested categories.
These distinguish requests, actual simulations, and internal adjudication work.

Planned improvements
--------------------
Still to implement:
    - Convergence checks and bounded extra work inside fixed-pool solving.
    - Exact expected payoffs when the joint-action space is small enough.
    - Response construction guided by likely opponent plans.
    - Stronger non-learned continuation policies and positional evaluation.
    - A repeatable full-game runner and broader playing-strength comparisons.

Machine learning can later supply stronger action priors and value estimates.
The current interfaces provide those integration points; the present code
does not yet reproduce the full Diplodocus training and playing system.
