POLICY SEARCH CONTRACT

PolicySearch.search(game, power)                             ==> SearchResult
BestResponseSearch and DiLPiKLSearch implement PolicySearch.
adaptive.asSearch(initialLimit, generator, priorFactory) supplies the same
interface. Each call generates fresh pools; the prior factory binds each
movement root. Other phases skip discovery and prior binding.
adaptive.search(...) retains its reports.
ResponseDiscovery discovers additions; it does not select a complete policy.

SearchResult.distribution is the policy to sample. meanValues are aligned raw
payoff means: fixed anchor opponents for BestResponseSearch, sampled history
for DiL-piKL.
They exclude search penalties and are not fresh returned-policy evaluations.
samplesPerCandidate counts observations per mean, including cached payoffs,
but excluding extra evaluator rollouts and earlier adaptive solves.
Root pools must contain distinct complete actions and positive prior support.
BestResponseSearch may select an individual zero-prior action; DiL-piKL assigns it no mass.
BestResponseSearch and ResponseDiscovery share fixed-sample payoff measurement;
each retains its own sampling order and candidate-selection rules.


FIXED-POOL BASELINE

PaperSearchProfile implements SearchProfile.
PaperSearchProfile.forState(snapshot)
    -> Spring 1901 movement: uniform {10^-2, 10^-1.5, 10^-1, 10^-0.5}; play 10^-2
    -> later turns: uniform {10^-4, 10^-3, 10^-2, 10^-1}; play 10^-4
    -> ADAPTIVE temperature; caller supplies iterations and seed

profile.solver(evaluator, generator, limit, iterations, seed) ==> DiLPiKLSearch
profile.solver(..., seed, PolicyOutput.AVERAGE)               ==> averaged output
solver.search(game, power)                                  ==> SearchResult
solver.solve(game, pools, trials)                           ==> JointSearchResult
solver.trace(game, pools, checkpoints, trials)               ==> List<JointSearchResult>

search() generates pools; solve() accepts explicit pools. Both validate them.
    -> freeze complete, distinct actions and anchor probabilities
    -> initialize Q = 0 and per-type utility statistics
    -> each iteration:
         -> form policies from previous Q and temperature
         -> accumulate each type's probabilities, including the playing type
         -> independently sample a lambda and action per nation
         -> freeze opponents; evaluate each nation's alternatives
         -> update equal-weight mean payoffs Q and per-type utility statistics
    -> return selected playing policies, population mixtures, Q, and temperatures

policy(a) proportional to exp((Q(a) + lambda * logPrior(a)) / (kappa + lambda))
kappa_t = 3 S_t / (10 sqrt(t)); S_t measures per-type policy-averaged utilities.
Startup is uniform over positive-prior actions. Zero-prior actions stay excluded.
Older solver constructors without a schedule retain ZERO temperature.
Older factories and constructors retain FINAL output.
FINAL uses the policy after the last update. AVERAGE uses the equal-weight
average of pre-update policies from iterations 1 through T, including startup.
The output choice does not change sampling, Q, temperatures, or evaluation work.
JointSearchResult retains immutable Settings: population, playing lambda,
and temperature schedule. Construction validates the selected policies.
solved.withOutput(choice) selects either output from the same solve.
Selecting the existing output returns the same result.
The profile-taking overload checks the recorded settings exactly.
Manually constructed results must also supply settings and temperatures.
trace() takes increasing checkpoints ending at the iteration budget.
It records one continuous solve; no restart, extra sampling, or extra trials.
Each immutable snapshot reports its own completed iteration count.

Same root and payoff function as the solve:

Temperature always means final recorded kappa, even for an averaged policy.
All checks concern retained actions; none certifies full-game equilibrium.

LEARNED PROPOSALS AND COMPARISON

new PolicyActionGenerator(proposalPolicy, anchorPolicy) -> ActionGenerator
generator.generate(request, catalog) -> immutable complete action candidates
generator.propose(request, catalog) -> candidates plus proposal probabilities
generator.propose(request, fullEncoding) -> reuse an existing movement catalog

Movement proposals use at most 256 distinct actions and 32 draws per target
candidate. The target is capped by the supplied mask's joint action count.
No all-hold or greedy action is inserted. First occurrences retain sample order.
Duplicate-heavy policies can return short pools; Result reports draws and
duplicates. Its logProposal values describe action probabilities before
deduplication, not inclusion probabilities or pool-normalized weights.
Retreats and adjustments delegate to UniformActionGenerator by default.
An explicit constructor accepts another fallback and a positive draw multiplier.

Proposal and anchor are independent immutable MovementPolicy instances.
Changing only the anchor cannot change sampled orders. The same instance is
prepared once when both use the full mask. All work is local to the invocation;
no root or unbounded prepared-state cache is retained.
Catalog restrictions change the proposal's input masks, so its probability is
defined for that input. The anchor always receives the full root encoding.
candidate.logPrior remains the full-action anchor log probability even as
candidate limits or scopes change. It is never renormalized over the pool.
Zero anchor support remains negative infinity; a wholly zero-prior pool cannot
be searched. Invalid model distributions or generated actions fail explicitly.
No matching-support or complete-convoy constraint is imposed beyond catalog
legality. The current factorized model can generate uncoordinated orders.
For adaptive search pass generator and anchorPolicy::bind together. A scoped
wrapper likewise needs new ScopedActionGenerator(generator, scope,
anchorPolicy::bind); its older default anchor is convoy-free uniform.

new HybridActionGenerator(proposalPolicy, anchorPolicy) -> ActionGenerator
hybrid.propose(request, catalog or fullEncoding) -> candidates and selection counts

The hybrid caps its target at 256 and the supplied mask's joint action count.
Each child constructs up to that target once, using the request's unchanged
seed. Half the retained places are reserved for each child; an odd extra place
goes to learned proposals. It takes learned reservations first, then distinct
heuristic reservations. Remaining places use unused learned candidates, then
unused heuristic candidates. A one-place pool only calls the heuristic when
the learned child returns no action. No retries or uniform padding are added.
Child duplicates are errors; cross-child duplicates retain the first selected
action and source. Exact Fleet destinations remain distinct during deduplication.
Result reports child availability, cross-child overlap, quotas and retained
counts. Counts describe selection, not probabilities. The hybrid can return
a short pool when the distinct union is too small. Each retained action is
rescored under the full-root anchor; no orders are repaired or filtered.
Its explicit constructor accepts two ActionGenerator children, a MovementPolicy
anchor and a nonmovement fallback. The default fallback is unchanged uniform.
Adaptive and scoped use requires the same anchorPolicy::bind as learned proposals.

MovementCoordination.inspect(root, candidate) counts own-support and own-convoy
orders with mismatched referenced orders. It requires a complete movement action;
CatalogActionValidator remains responsible for legality. Support matching uses
OrderForms.supportMatches and current locations, including canonical coasts.
Convoys require the referenced own Army to move to the convoy's destination.
Foreign coordination, convoy paths, support cutting, bounces and final outcomes
are outside this check. Matching orders do not guarantee successful moves.

PolicyProposalExperimentApp compares UNIFORM, PLAUSIBLE, FULL_UNIFORM, LEARNED,
and HYBRID. The hybrid is an engineering comparison, not the Diplodocus network.
The first two retain their convoy-free proposals and inserted all-hold action.
FULL_UNIFORM uses zero-weight LinearMovementPolicy over the full legal catalog,
with the same sampler as LEARNED. This controls for the larger convoy-capable
action space when assessing the learned proposal. HYBRID uses learned and
plausible children with the same individual budgets and seeds as those controls.
It may construct twice as many candidates before selecting its retained pool.
Its generation work is larger even when search and fresh-evaluation work match.
Every pool is rescored under the same supplied anchor, including the legacy
methods. This is a proposal comparison, not a replay of old agent defaults.
The loaded proposal model scores every printed action for likelihood comparison;
that column does not describe how a heuristic constructed its candidate.

Each method gets the same pool/search seeds, candidate limit and iteration
budget. DiL-piKL returns AVERAGE under the existing PaperSearchProfile.
The continuation policy stays convoy-free uniform with fixed count/seed,
using SUM_OF_SQUARES at the first winter boundary. All processors use JUDGE,
one trial and seed zero. No real move is submitted or stored.

Independent full-anchor opponent samples are drawn once and reused across
all methods and alternatives. They are not drawn from truncated candidate
pools or either solve's learned opponent mixture. Fresh search-policy scores
and paired differences from UNIFORM include opponent-sampling standard errors.
PLAUSIBLE and subsequent methods also report differences from PLAUSIBLE;
HYBRID additionally reports its difference from LEARNED. Each paired error is
computed from per-sample differences, not by subtracting separate errors.
Mixture errors are computed per shared sample, preserving action covariance.
These estimates depend on the fixed pools, search, weak continuations and
rollout seed; they are not win rates or equilibrium certificates. best_in_pool
is selected on those same samples and is optimistic. Raw Q is not a comparable
fresh score across solves. The experiment does not tune against test data.

OPENING is the standard Spring 1901 board. CONTACT is a constructed Fall 1902
board with armies in contact and fleets at sea; it is not a historical replay.
Both are independent of the training dataset. --power filters tables only;
all powers are searched and evaluated. Actual pool sizes, proposal draws,
duplicates, root evaluation counts, model hashes and timings are printed.
Hybrid child availability and selection counts accompany each power's pool.
Each candidate has own-support and own-convoy mismatch counts. Pool summaries
count actions with each kind, their union, and search mass assigned to that union.
Short pools use fewer evaluations, and budgets are not wall-time matched.
Generation timing excludes loading and shared reference-policy preparation.
