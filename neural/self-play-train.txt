TYPE-CONDITIONED SELF-PLAY POLICY LEARNING

CPU training continues to use the existing environment and neural/requirements.txt.
The optional CUDA path is described below and uses a separate environment.
Run from the repository root. In CPU examples, python means the interpreter
from the existing training environment.

First run the full numerical self-check:

  python -m neural.test_self_play_train --spec data/self-play-cache-v1/value/specification.json

Then check the current smoke cache without training:

  python -m neural.self_play_train --cache data/self-play-cache-v1 --initial-policy data/movement-gru-v1/policy.pt --anchor data/movement-linear-v1/policy.bin --verify-only -v

The initial policy is the Python .pt checkpoint, NOT either Java model.bin.
Hidden size is taken from that checkpoint, never supplied independently.
The smoke cache has no VALIDATION policies. Verification reports that explicitly
and performs no optimization or checkpoint writes. Attempting to fit it fails
before creating an output directory.

After generating independently seeded self-play games and caches containing
both policy splits, use a NEW output directory, for example:

  python -m neural.self_play_train --cache data/self-play-cache-round1 --initial-policy data/movement-gru-v1/policy.pt --anchor data/movement-linear-v1/policy.bin --output data/movement-self-play-v1 --epochs 3 --batch-size 8 --candidate-batch-size 32 --max-options 16384 --learning-rate 0.0001 --threads 4 -v

--cache accepts multiple cache directories. Duplicate games and mixed split
seeds across them are rejected. Keep the same self-play split seed across
rounds. The optimizer/randomization --seed is a separate setting.
CPU is the default. --device cuda requires an available compatible runtime;
unsupported deterministic kernels fail rather than silently falling back.

CUDA execution
--------------
The validated Windows environment uses Python 3.12 and PyTorch 2.14.1+cu130
in .venv-cuda. Use that interpreter for the first integrated GPU run:

  .\.venv-cuda\Scripts\python.exe -c "import torch; print(torch.__version__); print(torch.version.cuda); print(torch.cuda.is_available())"

The existing neural/requirements.txt remains the CPU environment's dependency
specification. Do not install it into .venv-cuda: its torch==2.6.0 pin would
replace the newer CUDA build. No new installation is needed for the already
working .venv-cuda environment. Preserve the original .venv.

--device cuda selects deterministic float32 CUDA execution with TF32 disabled.
The runtime uses the modern IEEE precision controls when available and the
legacy TF32 controls on older PyTorch; it never mixes the two APIs. cuDNN
benchmarking is disabled. Model parameters are float32; target weighting and
whole-action accumulation retain their existing float64 arithmetic.
Mixed precision, compilation and prefetch are not enabled.

CUBLAS_WORKSPACE_CONFIG defaults to :4096:8 before CUDA computation begins.
Any different value is rejected for this validated configuration. Remove
TORCH_ALLOW_TF32_CUBLAS_OVERRIDE=1 before starting Python. Missing CUDA support
or unsupported deterministic kernels cause an explicit failure.

Allocation filling remains enabled by default for CUDA. The opt-in flag

  --device cuda --no-fill-uninitialized-memory

disables PyTorch's protective initialization of otherwise uninitialized
allocations during policy updates and evaluation. Deterministic algorithms,
necessary zero initialization, finite-value checks and optimizer behavior
remain enabled. The previous fill setting is restored afterward, including
when an update or evaluation raises. Model loading and checkpoint serialization
run outside this scope. Other trainers and CPU execution are unchanged.
The flag is rejected without --device cuda.

The audited policy path builds complete input tensors, initializes its
accumulators and loads complete checkpoint state. The bounded CUDA experiment
found identical guard-on/off predictions, gradients, optimizer state and final
parameters. This option still requires fresh validation if that path changes;
it is not a global allocation policy for unrelated code.

For the first full integrated training/validation cycle, use a NEW candidate
directory and keep the frozen v5 initialization and round-five caches:

  .\.venv-cuda\Scripts\python.exe -m neural.self_play_train --cache data/self-play-round5-main/batch-00/batch/cache data/self-play-round5-main/batch-01/batch/cache data/self-play-round5-main/batch-02/batch/cache data/self-play-round5-main/batch-03/batch/cache --initial-policy data/movement-self-play-v5/policy.pt --anchor data/movement-linear-v1/policy.bin --output data/gpu-main-validation-v1 --epochs 3 --batch-size 8 --candidate-batch-size 32 --max-options 16384 --learning-rate 0.0001 --weight-decay 0.0001 --gradient-clip 1.0 --threads 4 --seed 7 --device cuda --no-fill-uninitialized-memory -v

This runs initial validation, three complete TRAIN epochs, validation after
each epoch, held-out checkpoint selection and selected-checkpoint readback.
It writes a new policy.pt and training.json. It does not promote the candidate
or touch TEST data. Retaining epoch 0 remains a valid outcome.

training.json records the effective device, precision API, allocation-fill
setting, CUDA/cuDNN versions and GPU identity under runtime. Epoch timings
include their validation pass, as before; they cannot be compared directly
with the temporary experiment's isolated training-batch totals. Checkpoint
and training-receipt schemas remain compatible with neural.self_play_export.

The trainer has no dependency on gpu_experiment.py, gpu_profile.py or
gpu_fill_experiment.py. Archive completed temporary scripts with their reports:
their recorded source hashes no longer match this integrated trainer.
Keep production adoption deferred until the full-cycle report is reviewed.

Model
-----
TypeConditionedGRU reuses the existing movement GRU and its full legal masks.
Its new initial recurrent state is:

  base_initial + tanh(type_projection(type_features))

The projection has no bias. A supervised warm start copies every old tensor
and initializes only this new projection to zero, preserving old predictions.
All GRU and adapter parameters can then learn. The separate human anchor is
hashed for identity checks and is never a parameter or optimization target.

The 11 type features are float32 log10 values of the playing lambda and four
population lambdas, the four float32 population weights, and FINAL/AVERAGE
one-hot flags. The logarithm is computed in float64 before float32 conversion;
there is no clipping. Profile IDs are checked metadata, not another embedding.
Current archives contain phase-based types only. This does not establish
generalization to arbitrary unseen lambda assignments.

Training admits COHERENT_GRU_HYBRID DiL movement targets whose recorded anchor
matches --anchor. Uniform/heuristic-root targets are not silently treated as
human-anchor-conditioned data. Different producer checkpoints are permitted
and recorded, but the human anchor must remain the same.

Loss and batching
-----------------
The objective is mean over ROOT DECISIONS of:

  -sum_candidate q(candidate) * sum_slot log P(order | its own prefix, board, type)

q is the recorded search probability, retained at float64 precision.
Each candidate keeps its complete action and its own autoregressive prefix.
The decoder normalizes over the full legal options of the current slot,
NEVER only over the retained candidates. No per-slot marginals replace q.
Selected actions, anchor priors, historical search means and outcomes are
not predictive inputs or extra labels. No second anchor penalty is added.

--batch-size counts root decisions per optimizer update.
--candidate-batch-size and --max-options bound each candidate microbatch.
The latter counts the full legal options repeated for each included candidate.
A whole candidate is never truncated. An oversized candidate fails preflight.
Exactly zero-weight candidates are omitted from forward/backward work.

Each microbatch loss uses the SAME total root-minibatch denominator.
Gradients accumulate across all positive-weight candidates; clipping and the
optimizer step occur once afterward. This preserves root weighting, including
the final short batch. No division by candidates or unit/order count is used.
Smaller microbatches reduce memory, not the intended objective; floating-point
roundoff can still vary slightly with packing/device.

CPU batch profiling
-------------------
Use neural.self_play_profile for a bounded timing run on existing approved
caches. It shares the trainer's train_batch implementation and uses a fresh
in-memory model and AdamW optimizer. Updates exercise real training computation;
the modified model is discarded. Only profile.json is written to a NEW output
directory. Source checkpoints, anchor files and caches remain unchanged.

First run the profiling checks:

  python -m neural.test_self_play_profile --spec data/self-play-round5-main/batch-00/batch/cache/value/specification.json

Then run the measurement:

  python -m neural.self_play_profile --cache data/self-play-round5-main/batch-00/batch/cache --initial-policy data/movement-self-play-v5/policy.pt --anchor data/movement-linear-v1/policy.bin --output data/self-play-profile-v1 --batches 32 --warmup-batches 4 --batch-size 8 --candidate-batch-size 32 --max-options 16384 --threads 4 --seed 7 -v

This command supports CPU execution only. --threads controls PyTorch's CPU
threads and is independent of the eight Java replay/cache workers. No Java
compilation or SQLite access is needed; a running scraper can continue.
Other processes can influence the timings.

The cache reader loads and verifies all cache bytes before the batch loop.
Startup verification/indexing and model/optimizer setup are reported separately.
Repeated input preparation therefore measures work on those resident bytes:

  root_decoding       Seeded batch selection and decoding cached root examples.
  candidate_planning  Target checks and positive-weight candidate microbatching.
  tensor_assembly     Type features, arrays, tensors and full legal-mask layout.
  forward_loss        Neural predictions and complete-action loss computation.
  backward            Gradient computation for each candidate microbatch.
  optimizer           Gradient reset, clipping, AdamW update and parameter checks.
  other               Remaining batch bookkeeping and measurement overhead.

Preparation combines the first three rows. Model computation combines the next
three. All times are nonoverlapping wall-clock seconds; they include waiting or
CPU contention while the measured operation runs. Progress printing and report
writes are outside the measured batch intervals.

The first --warmup-batches updates use the same temporary model/optimizer and
are excluded from the measured totals. Then exactly --batches updates are
measured in the existing first-epoch TRAIN shuffle. The command rejects a count
larger than that split can supply; it never cycles or silently shortens the run.
The final short minibatch, when selected, retains normal root weighting.

Existing admission, anchor, split-seed, duplicate and option-limit checks still
apply. Cache verification includes stored VALIDATION/value data, but optimizer
steps use TRAIN only. No validation evaluation, model selection, value fitting,
TEST evaluation, checkpoint export or promotion is performed. Profiling allows
an empty VALIDATION split; it does not make such a corpus ready for fitting.

profile.json contains source receipts, settings, startup durations, every
warm-up/measured batch, and separate summaries. complete=true is written only
after all requested steps and source-checkpoint/anchor readback checks succeed.
An interrupted or failed run retains an incomplete report. Retry with a fresh
output directory. Prefetching is not enabled by this measurement.

Selection and artifacts
-----------------------
Both TRAIN and VALIDATION must contain policy roots for fitting. Membership is
never repaired by moving positions between splits. Whole-action cross-entropy
averaged over held-out root decisions selects the checkpoint. Target entropy,
KL, uniform-mask cross-entropy, game-mean cross-entropy and subgroup losses
are reported, but they do not constitute playing-strength measurements.

The initialization is candidate epoch 0. Only strict validation improvement
replaces it; ties retain the earlier checkpoint. A completed run can correctly
retain epoch 0 and report improved_over_initial=false.

The new directory contains policy.pt and training.json. The latter remains
incomplete until the selected checkpoint reloads and reproduces its validation
score. Keep the baseline and source archives. Existing outputs are rejected.
The checkpoint binds the movement/type specifications, frozen anchor, initial
policy, self-play split seed and input cache fingerprints.

A subsequent compatible typed checkpoint can also be used as --initial-policy.
Its anchor and self-play split seed must match. This is a warm start with a
fresh optimizer, not interrupted-run resumption.

This checkpoint has a NEW schema. Do not pass it to the old neural.export
command. Use neural.self_play_export and the matching Java type-conditioned
loader, then pass Java parity before selecting the new model for self-play.
See neural/self-play-export.txt for the exact commands and provenance checks.
No value model, TEST payload, automatic promotion or baseline file is changed.

Checks
------
The full self-check covers unchanged initial predictions, complete-action loss,
zero-weight exclusion, chunk-invariant gradients, finite-difference type
gradients, causal prefixes, joint-target learning, held-out selection,
checkpoint reload, epoch-zero ties and output/preflight guards.
The separate profiling check covers timed/plain update equivalence, profiling
stage boundaries, warm-up exclusion, bounded TRAIN-only execution, unchanged
source files and incomplete-report handling.

The device-runtime checks are separate so --data-only stays standard-library
only:

  python -m neural.test_self_play_device

They cover CPU-default preservation, CUDA precision API selection, flag and
environment guards, scoped fill restoration, CLI wiring, and complete
fit/selection/checkpoint-readback behavior. Local CUDA-path fixtures execute
tensors on CPU explicitly; the command above does not certify CUDA kernels.
The full CUDA training command is the user-machine integration validation.

The neural.test_self_play_train command uses a synthetic map with explicitly
test-only hash bindings when --spec is omitted. With --spec it verifies the
actual frozen Java value/movement specifications. Its fixtures and checkpoints
remain temporary; existing weights are untouched. --data-only runs the
standard-library checks without NumPy/PyTorch. It does NOT run the
numerical/model tests and is not a substitute for the full check.
